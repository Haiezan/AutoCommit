# AutoCommit 提交体验优化设计

日期：2026-11-17

状态：待用户复核

## 目标与边界

让用户在 Visual Studio 中清楚知道将读取、发送和提交哪些变更，并能判断模型配置、草稿和变更是否仍然匹配。首期聚焦已有 Git 与 TFVC 流程，不增加自动暂存、自动推送、模型切换或新的版本控制能力。

本设计基于源码与仓库文档。VS 2019/2022 的实际窗口表现、真实模型调用和 TFVC 服务联调尚未验证，交互细节需要在这两类环境中验收。

## 当前流程与问题

工具窗口自动识别项目并读取变更。读取调用 `ProjectConfiguration.Initialize`，会在尚无配置的目录中创建 `.auto` 文件。模型配置、变更摘要、生成结果和操作按钮集中在同一窗口。Git 读取暂存区并提交到本地；TFVC 读取所选目录下递归范围的全部挂起更改并签入服务器，不采用 Team Explorer 的勾选范围。

当前界面存在四个容易误解的状态：读取看起来是只读操作却会写项目文件；TFVC 仍显示“暂存差异”等 Git 术语；模型地址或名称修改后，“连接成功”可能仍指先前配置；过期说明可以直接复制，提醒在复制之后才出现。README 与项目内的旧说明还给出了互相冲突的 TFVC 支持信息。

## 推荐方案

采用“流程与信任感优先”的渐进改造，保留单窗口和现有核心操作。先修正读取、状态、复制和 TFVC 签入确认，再整理安装与使用文档。仅修改文案不足以消除意外写文件和过期复制；全面重做窗口会推迟这些高风险问题的解决。

### 1. 读取与项目配置

- “读取变更”只识别仓库、读取变更、读取已有配置，不创建或修改项目文件。
- 若 `.auto/model.json` 不存在，界面在内存中使用本机默认模型设置；若 `.auto/commit-rules.md` 不存在，使用内置规范。显示配置来源为“本机默认”或“内置规范”。
- 将保存按钮明确命名为“保存项目配置”或“保存本机默认配置”，名称由当前是否识别到项目决定。用户选择保存项目配置时，界面在执行前说明将创建或更新的 `.auto` 文件；保存动作才调用项目配置初始化与写入。API Key 继续只在本机加密保存。
- 生成只使用当前界面中的设置和规范，不隐式保存配置。配置尚未保存时允许生成，并显示“本次设置尚未保存”。
- 已有 `.auto` 文件的读取和加载规则保持原有优先级。用户临时修改规范时，切换仓库或重新加载仍须确认覆盖。

### 2. Git 与 TFVC 的范围呈现

- 读取后显示版本控制类型、目录或仓库、分支或工作区、变更数量和文件清单。Git 文案使用“暂存变更”“提交到本地”；TFVC 文案使用“挂起更改”“签入服务器”。
- TFVC 文件清单使用读取时获得的结构化路径和操作类型，而非从预览文本反向解析。确认页展示工作区、选定目录、递归范围、完整文件清单、提交说明以及“服务器签入”的后果。文件较多时清单可滚动，数量始终可见。
- TFVC 确认页明确写明“不采用 Team Explorer 勾选项”。默认焦点为取消；最终按钮为“签入服务器”。Git 确认页继续明确“不推送”。
- 确认前及真正提交前沿用现有快照校验。发生变化时保留说明，阻止提交并引导重新读取。TFVC 的团队策略、冲突与门控行为保持现状。

### 3. 模型连接与草稿状态

- 模型连接状态只对应当前服务地址、模型名称、HTTP 选项和 API Key。任一值改变或切换项目后，原“连接成功”立即变为“当前设置尚未测试”；保存状态单独显示，不等同于连接测试成功。
- “生成中”“待审核”“已手动编辑”“已过期”“已提交”继续作为草稿状态。变更重新读取后，只有快照一致的草稿可直接提交。
- 点击复制时重新读取当前范围并核对草稿快照。若变更已变化、草稿已提交或无法确认当前变更，先显示原因，再让用户选择“重新读取”或“仍复制此说明”；未明确选择前不写入剪贴板。正常复制保留当前异步重试和失败时选中原文的行为。
- 错误提示附带下一步动作，例如“重新读取变更”“检查模型设置”“转到 Team Explorer 完成签入”；保留具体错误原因供排查。

### 4. 文档与安装入口

- README 顶部给出按 VS 2019/2022 区分的可用安装包、版本、支持能力和实际验证状态。下载指向仓库中存在的发布包，不指向构建后才出现的 Debug 路径。
- 当前仓库的发布包矩阵应准确标为：VS 2019 有 0.6.1 包（代码包含 TFVC，但缺少真实服务联调）；VS 2022 最新可用包为 0.5.0（Git 版本）。VS 2022 源码清单虽为 0.6.1，仓库尚无对应发布包，不能将其列作可下载版本。
- 删除或明确标注旧版本的“TFVC 尚未实现”等过期指引。更新仓库现有的 `.auto/README.md`；项目配置初始化时生成的 README 与当前能力保持一致。
- 首次使用步骤按实际顺序描述：选择范围、配置模型、检查发送内容、生成审核、复制或提交。明确模型测试会产生请求费用，生成会发送预览中的代码和规则。

## 组件与数据流

`RepositoryProvider` 与 Git/TFVC provider 负责读取快照和结构化文件清单；`CommitControl` 只根据快照状态展示信息和触发操作。项目配置读取与初始化拆开：读取返回已有配置或内存默认值，保存才写文件。模型设置状态在界面侧跟踪当前输入是否经过测试与保存，API Key 不进入项目文件或状态日志。复制、生成、提交均以当前快照为依据；生成与提交保持现有前后或执行前校验。

## 验收标准

1. 新项目首次打开并点击“读取变更”后，磁盘上不会新建 `.auto`；明确保存项目配置后才创建，且用户能看见写入位置。
2. Git 与 TFVC 界面均使用对应术语。TFVC 用户在确认前可看见本次签入的所有文件、目录范围和服务器写入提示；取消不会签入。
3. 修改地址、模型、HTTP 选项或 Key 后，连接状态立即变为“当前设置尚未测试”；项目切换亦如此。保存配置不显示为连接成功。
4. 变更变化、已提交或快照读取失败时，复制前出现对应提示；选择取消或重新读取不会覆盖剪贴板；选择“仍复制”才复制。
5. 生成失败、取消或快照变化仍保留原说明；提交前快照变化仍阻止提交。原有撤销、剪贴板重试、Git hooks 与 TFVC 策略行为不回退。
6. README 与项目配置说明对 Git/TFVC、VS 版本和发布包的描述一致，所有指向的安装包在仓库中存在。

## 验证方式与后续候选

先用现有自动化测试覆盖“只读读取”、状态失效、过期复制和快照变化；再在 VS 2019、VS 2022 中检查窄窗口、键盘导航、浅色/深色主题及实际安装流程。TFVC 签入范围、认证、策略与门控需在测试工作区和真实服务器验收，未通过前不宣称企业场景可用。

目录选择器、敏感内容检查、模型切换、规范本地校验和流式输出属于后续候选，不纳入首期验收。
